# Wind Power Forecasting — frontend аналитики ВЭС

Wind Power Forecasting — название проекта и сайта; HEALTH CORE — команда.

Vue 3 + Vite. Запуск из этой папки: `npm ci`, затем `npm run dev`.
Открыть http://127.0.0.1:5173. Для сборки: `npm run build`.
Node.js 20.19+ или 22+. Внешние шрифты и CDN не нужны.

Vite читает клиентские настройки из корневого `.env` репозитория (`envDir: ..`). API по умолчанию: http://127.0.0.1:8000; для сервера собирайте с `VITE_API_URL=/api`. Необязательный `VITE_GOOGLE_MAPS_API_KEY` включает встроенную карту. Без него список координат и ссылки на Google Maps всё равно работают. Клиентские `VITE_`-переменные встраиваются в браузерный код: серверные секреты и `API_WRITE_KEY` туда помещать нельзя.

Backend запускается по корневому README. При первом запуске он автоматически импортирует конкурсные CSV из `TZ_DIR` и обучает модель, если ревизий в БД ещё нет. Интерфейс опрашивает `GET /readiness`, показывает импорт, обучение либо конкретную причину недоступности и блокирует новый прогноз до готовности. Без backend доступен интерфейс с пустыми состояниями; графики не заполняются вымышленными данными.

Раздел «География ВЭС» использует Google Maps и напрямую из браузера запрашивает для координат турбин скорость и направление ветра на высоте 100 м из архивного выпуска ECMWF IFS через Open-Meteo Single Runs API. Выберите дату выпуска и час (1–48), включите/выключите слой или запустите почасовое воспроизведение. Стрелка на карте показывает, куда дует ветер; в списке указано, откуда он дует. Подписи остаются привязаны к турбинам при изменении масштаба. Это архивный прогноз погоды, не фактическое измерение и не непрерывное поле между турбинами. Слой не меняет данные backend или БД. Для его работы браузеру нужен доступ к Open-Meteo; при ошибке источник показывает сообщение, а карта с турбинами остаётся доступной.

Для уже подготовленной Supabase БД запустите backend из корня репозитория в PowerShell:

```powershell
$env:DB_INIT_ON_STARTUP='false'
$env:PGSSLMODE='require'
.\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

Строка PostgreSQL подключения должна находиться в корневом `.env`. Режим `DB_INIT_ON_STARTUP=false` проверяет соединение, но не меняет схему и не включает RLS повторно. Используйте его только после первоначальной инициализации таблиц. Сохранённые прогнозы можно открыть по ID без артефакта модели; для нового прогноза бинарный артефакт берётся из БД либо из локального кэша старой ревизии.

## Проверка

1. Выберите 31.01.2026, запустите агента. Запрос создаёт 48-часовой прогноз двух турбин.
2. Переключите турбину: должно быть 48 точек. Переключите горизонт на 24: должно быть 24 точки этого же расчёта.
3. Переключите мощность / ветер / температуру. Наведение и ползунок выбирают час; точные числа доступны в таблице.
4. Экспортируйте CSV. Временные метки в CSV — UTC, в интерфейсе — UTC+5.
5. В источниках видны погодный выпуск, версия модели и отсутствующие метаданные. История загружается из БД после перезагрузки страницы; сохранённый запуск также можно открыть по ID.
6. Остановите API: новый запрос показывает ошибку и сохраняет предыдущий результат.

`node --test tests/model.test.js` проверяет границы времени, горизонты и диагностику пропусков.

## Границы текущего backend-контракта

Используются GET /health, GET /readiness, GET /forecasts, POST /forecasts/{date}, GET /forecasts/{id}.
API не предоставляет batch-задачу февраля, промежуточные агентные события, время публикации прогноза или доверительные интервалы. Эти возможности не имитируются. Ежедневные выпуски через интерфейс пока запускаются по одному; история показывает до 100 сохранённых расчётов.

В текущем backend naive `issued_at` означает UTC+5, naive `valid_at` и `weather_run_at` — UTC. Явный offset поддерживается и имеет приоритет. Сравнение времени инициализации погоды с выпуском ВЭС само по себе не доказывает отсутствие утечки будущих данных.

Реальный сквозной прогноз можно проверить только с подготовленной backend-моделью. Артефакт ревизии хранится в БД; локальный `model.joblib` не нужен. Браузерные проверки на тестовом API не являются проверкой точности модели. На публичном сервере `POST` требуют ключ оператора в верхней панели; он хранится только в `sessionStorage` вкладки.
