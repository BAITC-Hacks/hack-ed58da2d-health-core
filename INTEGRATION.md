## Выбранный путь

Сохраняем работающий контракт backend и расширенный UI Михаила. Это позволяет уже сейчас показать сквозной прогноз без переписывания маршрутов во время хакатона. Дальнейшие возможности из продуктовой спецификации добавляются к backend последовательно; frontend показывает только данные и статусы, которые тот действительно вернул. Масштаб прогноза — нормализованная мощность двух турбин, 0–1, без пересчёта в МВт.

## Действующий контракт

| Операция | Маршрут | Результат для интерфейса |
|---|---|---|
| Готовность | `GET /health` | `status: "ok"` |
| Исходные данные | `GET /measurements?turbine_id=1&limit=100&offset=0` | `original` сохраняет исходные значения CSV |
| Пополнение | `POST /measurements` | Добавление одного измерения; дубль даёт 409 |
| Расчёт | `POST /forecasts/{issue_date}` | `id`, `status`, `analysis`; всегда 48 часов по обеим турбинам |
| Просмотр | `GET /forecasts/{id}` | `issued_at`, `weather_run_at`, `model_version`, 96 точек |

Фронтенд посылает дату в формате `YYYY-MM-DD`, после `POST` загружает результат по `id`, фильтрует точки выбранной турбины и показывает первые 24 или все 48 часов. `issued_at` без смещения — локальное время Казахстана UTC+5; `weather_run_at` и `valid_at` без смещения — UTC. Это текущий временной контракт; лучше перейти к ISO 8601 со смещением в обоих слоях при следующем изменении API.

Погодный выпуск ECMWF выбирает backend, а не браузер. В интерфейсе уже есть проверка количества часов и диапазона нормализованной мощности. Проверка того, когда именно архивный прогноз стал доступен, и cutoff обучающих данных должны выполняться на backend и пока не заявляются как доказанные.
