# Health Core — прогноз выработки ВЭС

Конкурсный кейс HackAlem AI «Agentic AI для прогнозирования выработки ВЭС». Текущая версия хранит исходные измерения и турбины в БД, загружает CSV через интерфейс, создаёт выбираемые ревизии модели и строит почасовой прогноз на 48 часов для выбранных турбин по архивному выпуску ECMWF. План завершения и распределение работы — в [PLAN.md](PLAN.md); контракт backend и интерфейса — в [INTEGRATION.md](INTEGRATION.md).

## Что решаем

На каждый день с 31 января по 28 февраля 2026 года система должна воспроизвести решение, которое могло быть принято в тот день: получить доступный на тот момент прогноз погоды, подготовить признаки, применить обученную модель и сохранить результат на 24–48 часов. Расчёт запускается через API; последовательный прогон всего февраля и оценка по фактическим данным пока не реализованы.

Для расчёта на 00:00 времени Казахстана (UTC+5) используется выпуск ECMWF IFS за 12:00 UTC предыдущего календарного дня UTC. До момента решения остаётся около 7 часов на публикацию модели. Время выпуска, версия модели и входные погодные параметры сохраняются вместе с прогнозом. Прогнозная мощность — нормализованное значение `0–1` каждой турбины; перевод в МВт невозможен без номинальной мощности.

Исходные CSV из папки `TZ/` содержат 291 859 строк с 11 марта 2023 года по 31 января 2026 года, хотя в имени файлов фигурирует 28 февраля. CSV не входят в Git. Импорт сохраняет исходные поля каждой строки в `measurements.original` и отдельно числовые поля для вычислений. Обучение всегда читает БД, а не файлы CSV. По умолчанию оно исключает записи начиная с 31 января 2026 года, чтобы ревизию можно было использовать уже в прогнозе 31 января в 00:00. Для выпусков начиная с 1 февраля можно явно выбрать отсечение 1 февраля; тестовый февраль в обучение не допускается. Сервер отклоняет ревизию, если её последняя обучающая запись не предшествует моменту выпуска прогноза. Проверка модели использует последние 10% почасовых данных по времени. Фактическую ошибку февральского прогноза пока оценить нельзя. Модель обучается на измеренном ветре у турбины, а при прогнозе получает ветер ECMWF на высоте 100 м; эта разница распределений и неизвестное время публикации погодного выпуска ограничивают достоверность проверки.

## Состав и архитектура

- `backend/app/db.py`: PostgreSQL (включая Supabase) или локальная SQLite; исходные измерения, турбины, ревизии моделей, бинарные артефакты, запуски и точки прогноза. `init-db` создаёт таблицы, ограничения, индексы и включает RLS в PostgreSQL.
- `backend/app/pipeline.py`: импорт без дублирования по `(turbine_id, source_id)`, почасовая агрегация, обучение `HistGradientBoostingRegressor`, расчёт и простой анализ диапазона результата.
- `backend/app/weather.py`: архив отдельного выпуска ECMWF IFS через Open-Meteo Single Runs API.
- `backend/app/main.py`: FastAPI для просмотра и загрузки измерений, регистрации турбин, обучения, выбора ревизии и запуска прогноза.
- `frontend/`: интерфейс на Vue 3 с графиком, таблицей, выбором турбин и ревизии, загрузкой CSV, обучением и экспортом прогноза.

Цикл агента в текущей версии выполняется по запросу: выбор доступного выпуска погоды → загрузка → подготовка признаков → модель → контроль допустимого диапазона → запись результата. Автоматический повторный расчёт при обновлении входных данных, журнал состояний и обработка сбоев — задачи следующего этапа; они пока не заявляются как готовые.

## Зависимости и внешние источники

Backend зависимости с точными версиями зафиксированы в `requirements.txt`: FastAPI, Uvicorn, SQLAlchemy, Psycopg 3, pandas, NumPy, scikit-learn, joblib, HTTPX, python-dotenv, python-multipart. Frontend зависимости находятся в `frontend/package.json`, а точные версии Vue 3, Vite и их транзитивных пакетов — в `frontend/package-lock.json`.

Внешний погодный сервис: [Open-Meteo Single Runs API](https://open-meteo.com/en/docs/single-runs-api), модель ECMWF IFS HRES, доступ к конкретным архивным выпускам. Это исторические **прогнозы**, не реанализ и не фактическая погода. Источник данных — Open-Meteo с данными ECMWF; [лицензия API-данных CC BY 4.0](https://open-meteo.com/en/licence), атрибуция обязательна. [Бесплатный API](https://open-meteo.com/en/terms) разрешён для некоммерческого использования и имеет лимиты запросов; для коммерческого применения нужен соответствующий тариф. Две исходные координаты взяты из ссылок Google Maps в ТЗ; Google Maps также используется для раскрытия короткой ссылки при добавлении турбины. Supabase предоставляет PostgreSQL; приложение не использует его пользовательскую авторизацию или Storage.

## Развёртывание с нуля на Windows

Требуются Git, Python 3.11+ (`python --version`), Node.js 20+ и npm (`node --version`, `npm --version`), доступ к Open-Meteo. Команды выполнять в PowerShell из корня проекта. PostgreSQL в Supabase нужен для общей БД команды; локальную проверку можно провести с SQLite. Если репозитория ещё нет: `git clone https://github.com/BAITC-Hacks/hack-ed58da2d-health-core.git`, `cd hack-ed58da2d-health-core`, `git switch dev`.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
python -m backend.cli init-db
python -m unittest discover -s backend/tests -v
```

Перед `init-db` при использовании Supabase замените `DATABASE_URL` в `.env` по инструкции ниже. Без этого параметра либо с примером из `.env.example` используется локальная SQLite. Команда `init-db` не удаляет записи и её можно запускать повторно. Тот же bootstrap автоматически выполняется при старте API. В уже существующей БД `create_all` не меняет столбцы старых таблиц: последующие изменения схемы потребуют отдельной миграции.

Если есть конкурсные CSV, можно загрузить их из раздела «Данные и модели» в интерфейсе либо командами:

```powershell
python -m backend.cli import-csv 1 'TZ/Dataset HackAlemAI для участников 11.03.2023-28.02.2026 - turbine 1.csv'
python -m backend.cli import-csv 2 'TZ/Dataset HackAlemAI для участников 11.03.2023-28.02.2026 - turbine 2.csv'
python -m backend.cli train
```

Чтобы использовать весь январь для прогноза с 1 февраля, укажите `python -m backend.cli train --cutoff-date 2026-02-01`. Для прогноза, выпущенного 31 января в 00:00, такая ревизия не подходит и будет отклонена сервером.

Два конкурсных CSV не входят в репозиторий. Для воспроизведения их нужно положить в локальную `TZ/` с указанными именами либо передать другие CSV с теми же пятью столбцами. Импорт проверяет весь файл до записи, отклоняет нечисловые и недопустимые значения и повторяем: существующие пары `(turbine_id, source_id)` пропускаются. Для каждой новой турбины сначала добавьте координаты, затем её CSV и обучите новую ревизию. SQLite и локальный кэш модели не коммитятся; бинарный артефакт каждой новой ревизии сохраняется также в общей БД.

Запустите API в первом терминале (с активированным `.venv`):

```powershell
python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

Во втором терминале, из корня проекта:

```powershell
cd frontend
npm ci
npm run dev
```

Открыть `http://127.0.0.1:5173`. Для проверки API доступны `http://127.0.0.1:8000/docs` и `http://127.0.0.1:8000/health`: ответ должен содержать `"database":"ready"`. В интерфейсе откройте «Данные и модели», загрузите CSV для каждой турбины и нажмите «Обучить новую ревизию». Выберите ревизию и нужные турбины в панели прогноза. Для проверки выберите 31 января 2026 года, запустите агента и убедитесь, что получено по 48 строк на каждую выбранную турбину. Прямой запрос для первой турбины и ревизии с ID 1:

```powershell
Invoke-RestMethod -Method Post http://127.0.0.1:8000/forecasts/2026-01-31 -ContentType 'application/json' -Body '{"turbine_ids":[1],"revision_id":1}'
```

## База данных и доступы

Supabase-проект и сама база `postgres` создаются в кабинете Supabase; приложение не создаёт облачный проект. `python -m backend.cli init-db` в существующей базе создаёт таблицы `measurements`, `turbines`, `model_revisions`, `model_artifacts`, `forecast_runs`, `forecast_points`, ограничения и индексы, а также идемпотентно регистрирует две турбины из ТЗ. В PostgreSQL для всех шести таблиц включается RLS без политик для `anon`/`authenticated`: фронтенд работает только через backend, прямой доступ через Supabase Data API закрыт. На общей БД после обновления кода запускайте `init-db` явно: `DB_INIT_ON_STARTUP=false` пропускает DDL при обычном старте API. Bootstrap не изменяет столбцы существующих таблиц.

В локальном `.env` рядом с `.env.example` укажите `DATABASE_URL`. Файл `.env` игнорируется Git. В панели Supabase откройте **Connect → Connection string** и выберите Direct connection для ПК/постоянного сервера с работающим IPv6 либо Session pooler (порт 5432) для IPv4. Если Direct-хост `db.<project-ref>.supabase.co` не подключается на ПК без IPv6, используйте Session pooler, не Transaction pooler на порту 6543. Замените схему URL `postgresql://` на `postgresql+psycopg://` (приложение также делает это автоматически). Пример без реальных реквизитов:

```text
DATABASE_URL=postgresql+psycopg://USER:URL_ENCODED_PASSWORD@HOST:5432/postgres?sslmode=require
```

Для повседневной работы используйте отдельную роль с минимальными правами на таблицы; первичная инициализация требует права создавать объекты в `public` и включать RLS. Пароль с `@`, `:`, `/` и другими служебными символами необходимо URL-кодировать. Не отправляйте строку подключения в чат или репозиторий. Supabase API key и URL проекта для текущей архитектуры не нужны: backend использует PostgreSQL-соединение. Проверьте подключение командами `python -m backend.cli init-db` и `Invoke-RestMethod http://127.0.0.1:8000/health` после запуска API. При ошибке соединения старт API завершится с ошибкой, а не переключится молча на SQLite. Текущая версия создаёт начальную схему, но не содержит версионированных миграций последующих изменений.

### Перенос существующей SQLite в Supabase

Остановите локальный backend перед переносом, чтобы новые записи не появились в SQLite после снимка. Фронтенд останавливать необязательно. Для сохранности сделайте копию локальной БД (файл игнорируется Git):

```powershell
Copy-Item .\healthcore.sqlite3 .\healthcore-before-supabase.sqlite3
```

В `.env` добавьте `SUPABASE_DATABASE_URL=postgresql+psycopg://...` **или** замените существующий `DATABASE_URL` на полный URL из **Connect → Connection string** в Supabase. Если заданы обе переменные, `SUPABASE_DATABASE_URL` имеет приоритет. После успешного переноса и перезапуска backend приложение будет читать PostgreSQL. Не добавляйте URL в код, README или чат. Используйте роль с правами на создание таблиц и запись; целевые таблицы `measurements`, `forecast_runs`, `forecast_points` должны быть пустыми. Скрипт не смешивает данные с существующими строками и не удаляет их.

```powershell
.\.venv\Scripts\python.exe -m backend.migrate_sqlite_to_postgres
.\.venv\Scripts\python.exe -m backend.cli init-db
.\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

Скрипт копирует строки трёх исходных таблиц порциями, сохраняя ID, JSON и связи прогнозов; загрузка выполняется одной транзакцией. Он сверяет количество, максимальный ID и сумму ID каждой таблицы до и после коммита и обновляет PostgreSQL-последовательности. Новые таблицы турбин и моделей создаются bootstrap-командой, но скрипт не переносит в них ревизии из более новой SQLite. Если перенос не завершён, записи целевых таблиц откатываются и локальная SQLite остаётся нетронутой. Проверьте `http://127.0.0.1:8000/health`, затем откройте сохранённый прогноз по ID. Старый `model.joblib` — локальный артефакт; после переноса рекомендуется обучить новую ревизию, чтобы она сохранилась в `model_artifacts` и была доступна всей команде. Не удаляйте резервную SQLite, пока не проверите данные в Supabase.

## API и пополнение данных

- `GET /turbines` — список турбин и координат; `POST /turbines` — добавить `{name, latitude, longitude}` либо `{name, maps_url}`. Для коротких ссылок поддерживается только HTTPS Google Maps.
- `GET /measurements?turbine_id=1&limit=100&offset=0` — исходные строки для просмотра.
- `POST /measurements` — добавить одно измерение с `turbine_id`, `source_id`, `observed_at`, `wind_speed_ms`, `normalized_power`, `temperature_c`.
- `POST /measurements/upload?turbine_id=1` — загрузить CSV multipart-полем `file`, максимум 50 МБ; ответ `{rows, imported, skipped}`.
- `POST /models/train` — создать ревизию по данным БД до 31 января 2026 года (по умолчанию); тело `{"cutoff_date":"2026-02-01"}` разрешает использовать весь январь для выпусков не раньше 1 февраля. `GET /models` — список ревизий и метрик.
- `POST /forecasts/2026-01-31` с JSON `{"turbine_ids":[1,2],"revision_id":1}` — рассчитать 48 часов для указанных турбин выбранной ревизией. Без тела используются турбины, известные последней модели, и последняя ревизия.
- `GET /forecasts/{id}` — результат, погодные признаки и анализ.

Ревизия модели содержит метаданные и бинарный артефакт в PostgreSQL; локальный файл в `MODEL_DIR` — кэш и резервная копия. Другой ПК с доступом к той же БД может выбрать ревизию без копирования файлов. Модель не предсказывает для турбины без обучающих строк; сначала импортируйте её CSV и переобучите модель.

Публичная запись пока не защищена аутентификацией. При запуске на сервере API должен быть привязан к `127.0.0.1` и доступен через SSH-туннель. Перед публичным доступом нужны аутентификация, ограничения запросов, защита загрузок и отдельные права БД.

## Серверный запуск

Изолированный API размещается в `/opt/healthcore/api`, не затрагивая существующий `/opt/healthcore/ui`. На сервере Debian 12 с Python 3.11 создать виртуальное окружение, перенести `backend/`, `requirements.txt` и два исходных CSV в `/opt/healthcore/api/data/`, установить зависимости, скопировать `deploy/server.env.example` в `/opt/healthcore/api/.env`, выполнить `init-db`, два импорта и `train`. Сервисный файл `deploy/healthcore-api.service` запускает Uvicorn от отдельного пользователя `healthcore` только на loopback. Подробные команды для повторного развёртывания находятся в [deploy/README.md](deploy/README.md).

Для Supabase на сервере строку подключения размещают только в `/opt/healthcore/api/.env`, заменяя `DATABASE_URL`; после этого нужна повторная инициализация схемы и импорт в новую БД. Содержимое `.env` нельзя отправлять в Git. Переключение с SQLite на Supabase не переносит данные автоматически. Развёртывание на сервере выполняется только по отдельному запросу владельца.

## Ограничения

Нет февральских фактических значений для итоговой метрики. Нет автоматической очереди/периодического пересчёта, версионируемых миграций, калибровки смещения измеренного ветра к ECMWF и полного исторического прогона. Open-Meteo возвращает выбранный архивный выпуск, но не подтверждает точный момент его публикации. Выбор выпуска за 12:00 UTC предыдущего дня оставляет около семи часов запаса до решения; для строгой проверки доступности требуется независимый журнал публикации. Метрика MAE на измеренном ветре не является оценкой точности реальных февральских прогнозов.

В текущей общей БД ранее сохранённые прогоны за 31 января с прежними моделями помечены `invalid_lookahead`; их точки сохранены для аудита, но интерфейс запрещает экспорт как достоверного результата. Прогноз с новой ревизией, обученной строго до 31 января, сохранён отдельно.
