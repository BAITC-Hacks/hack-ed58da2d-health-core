# Health Core — прогноз выработки ВЭС

Конкурсный кейс HackAlem AI «Agentic AI для прогнозирования выработки ВЭС». Текущая версия — рабочий каркас: хранение исходных измерений двух турбин, загрузка CSV, обучение базовой модели, получение архивного прогноза погоды конкретного выпуска ECMWF и формирование почасового прогноза на 48 часов. План завершения и распределение работы — в [PLAN.md](PLAN.md); согласованный контракт backend и интерфейса — в [INTEGRATION.md](INTEGRATION.md).

## Что решаем

На каждый день с 31 января по 28 февраля 2026 года система должна воспроизвести решение, которое могло быть принято в тот день: получить доступный на тот момент прогноз погоды, подготовить признаки, применить обученную модель и сохранить результат на 24–48 часов. Расчёт запускается через API; последовательный прогон всего февраля и оценка по фактическим данным пока не реализованы.

Для расчёта на 00:00 времени Казахстана (UTC+5) используется выпуск ECMWF IFS за 12:00 UTC предыдущего календарного дня UTC. До момента решения остаётся около 7 часов на публикацию модели. Время выпуска, версия модели и входные погодные параметры сохраняются вместе с прогнозом. Прогнозная мощность — нормализованное значение `0–1` каждой турбины; перевод в МВт невозможен без номинальной мощности.

Исходные CSV из папки `TZ/` содержат показания только по 31 января 2026 года, хотя в имени файлов фигурирует 28 февраля. Поэтому фактическую ошибку февральского прогноза пока оценить нельзя. Метрика обучения ниже относится к отложенной части исторических измерений, а не к февралю и не учитывает погрешность прогноза погоды. Модель обучается на измеренном ветре у турбины, а при прогнозе получает ветер ECMWF на высоте 100 м; калибровка этого сдвига — ближайшая обязательная доработка.

## Состав и архитектура

- `backend/app/db.py`: PostgreSQL (включая Supabase) или локальная SQLite, исходные измерения, запуски прогноза и точки результата. При первом запуске создаются таблицы, ограничения, индексы; в PostgreSQL включается RLS.
- `backend/app/pipeline.py`: импорт без дублирования по `(turbine_id, source_id)`, почасовая агрегация, обучение `HistGradientBoostingRegressor`, расчёт и простой анализ диапазона результата.
- `backend/app/weather.py`: архив отдельного выпуска ECMWF IFS через Open-Meteo Single Runs API.
- `backend/app/main.py`: FastAPI для просмотра данных, добавления измерения и запуска прогноза.
- `frontend/`: интерфейс Михаила на Vue 3 с графиком, таблицей, переключением турбин и горизонта, источниками данных и экспортом CSV.

Цикл агента в текущей версии выполняется по запросу: выбор доступного выпуска погоды → загрузка → подготовка признаков → модель → контроль допустимого диапазона → запись результата. Автоматический повторный расчёт при обновлении входных данных, журнал состояний и обработка сбоев — задачи следующего этапа; они пока не заявляются как готовые.

## Зависимости и внешние источники

Backend зависимости с точными версиями зафиксированы в `requirements.txt`: FastAPI, Uvicorn, SQLAlchemy, Psycopg 3, pandas, NumPy, scikit-learn, joblib, HTTPX, python-dotenv. Frontend зависимости находятся в `frontend/package.json`, а точные версии Vue 3, Vite и их транзитивных пакетов — в `frontend/package-lock.json`.

Внешний погодный сервис: [Open-Meteo Single Runs API](https://open-meteo.com/en/docs/single-runs-api), модель ECMWF IFS HRES, доступ к конкретным архивным выпускам. Источник данных — Open-Meteo с данными ECMWF; [лицензия API-данных CC BY 4.0](https://open-meteo.com/en/licence), атрибуция обязательна. [Бесплатный API](https://open-meteo.com/en/terms) разрешён для некоммерческого использования и имеет лимиты запросов; для коммерческого применения нужен соответствующий тариф. Координаты обеих турбин предоставлены в ТЗ кейса через Google Maps. Другие внешние API не используются. Supabase, если выбран, предоставляет только PostgreSQL; работа приложения не зависит от его пользовательской авторизации.

## Развёртывание с нуля на Windows

Требуются Git, Python 3.11+ (`python --version`), Node.js 20+ и npm (`node --version`, `npm --version`), доступ к Open-Meteo. Команды выполнять в PowerShell из корня проекта. PostgreSQL в Supabase нужен для общей БД команды; локальную проверку можно провести с SQLite. Если репозитория ещё нет: `git clone https://github.com/BAITC-Hacks/hack-ed58da2d-health-core.git`, `cd hack-ed58da2d-health-core`, `git switch dev`.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
python -m backend.cli init-db
python -m unittest discover -s backend/tests -v
```

Перед `init-db` при использовании Supabase замените `DATABASE_URL` в `.env` по инструкции ниже. Без этого параметра либо с примером из `.env.example` используется локальная SQLite. Команда `init-db` не удаляет записи и её можно запускать повторно. Тот же bootstrap автоматически выполняется при старте API. В уже существующей БД `create_all` не меняет столбцы старых таблиц: последующие изменения схемы потребуют отдельной миграции.

Если есть конкурсные CSV, загрузите их и обучите модель:

```powershell
python -m backend.cli import-csv 1 'TZ/Dataset HackAlemAI для участников 11.03.2023-28.02.2026 - turbine 1.csv'
python -m backend.cli import-csv 2 'TZ/Dataset HackAlemAI для участников 11.03.2023-28.02.2026 - turbine 2.csv'
python -m backend.cli train
```

Два конкурсных CSV не входят в репозиторий. Для воспроизведения их нужно положить в локальную `TZ/` с указанными именами либо передать другие CSV с теми же пятью столбцами и указать их пути при импорте. Импорт повторяемый: записи с уже существующими `turbine_id` и `source_id` пропускаются. SQLite и обученная модель создаются локально и не коммитятся.

Запустите API в первом терминале (с активированным `.venv`):

```powershell
python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

Во втором терминале, из корня проекта:

```powershell
cd frontend
npm ci
npm run dev
```

Открыть `http://127.0.0.1:5173`. Для проверки API доступны `http://127.0.0.1:8000/docs` и `http://127.0.0.1:8000/health`: ответ должен содержать `"database":"ready"`. Без импортированных CSV доступны пустые таблицы, но прогноз не сформируется. После импорта и обучения проверочный сценарий: выбрать 31 января 2026 года, нажать «Сформировать прогноз», увидеть 96 строк (2 турбины × 48 часов), выпуск погоды и версию модели. То же напрямую:

```powershell
Invoke-RestMethod -Method Post http://127.0.0.1:8000/forecasts/2026-01-31
```

## База данных и доступы

Supabase-проект и сама база `postgres` создаются в кабинете Supabase; приложение не создаёт облачный проект. В существующей базе оно автоматически создаёт таблицы `measurements`, `forecast_runs`, `forecast_points`, ограничения и индексы. В PostgreSQL для этих таблиц включается RLS без политик для `anon`/`authenticated`: фронтенд работает только через backend, прямой доступ через Supabase Data API закрыт. Если одноимённые таблицы уже созданы вручную, проверьте их структуру: bootstrap не перезаписывает существующие столбцы.

В локальном `.env` рядом с `.env.example` укажите `DATABASE_URL`. Файл `.env` игнорируется Git. В панели Supabase откройте **Connect → Connection string** и выберите Direct connection для ПК/постоянного сервера с IPv6 либо Session pooler для IPv4. Замените схему URL `postgresql://` на `postgresql+psycopg://` (приложение также делает это автоматически). Пример без реальных реквизитов:

```text
DATABASE_URL=postgresql+psycopg://USER:URL_ENCODED_PASSWORD@HOST:5432/postgres?sslmode=require
```

Для повседневной работы используйте отдельную роль с минимальными правами на таблицы; первичная инициализация требует права создавать объекты в `public` и включать RLS. Пароль с `@`, `:`, `/` и другими служебными символами необходимо URL-кодировать. Не отправляйте строку подключения в чат или репозиторий. Supabase API key и URL проекта для текущей архитектуры не нужны: backend использует PostgreSQL-соединение. Проверьте подключение командами `python -m backend.cli init-db` и `Invoke-RestMethod http://127.0.0.1:8000/health` после запуска API. При ошибке соединения старт API завершится с ошибкой, а не переключится молча на SQLite. Текущая версия создаёт начальную схему, но не содержит версионированных миграций последующих изменений.

## API и пополнение данных

- `GET /measurements?turbine_id=1&limit=100&offset=0` — исходные строки для просмотра.
- `POST /measurements` — добавить одно измерение с `turbine_id`, `source_id`, `observed_at`, `wind_speed_ms`, `normalized_power`, `temperature_c`.
- `POST /forecasts/2026-01-31` — рассчитать 48 часов для двух турбин.
- `GET /forecasts/{id}` — результат, погодные признаки и анализ.

Публичная запись пока не защищена аутентификацией. При запуске на сервере API должен быть привязан к `127.0.0.1` и доступен через SSH-туннель. Перед публичным доступом нужны аутентификация, ограничения запросов и отдельные права БД.

## Серверный запуск

Изолированный API размещается в `/opt/healthcore/api`, не затрагивая существующий `/opt/healthcore/ui`. На сервере Debian 12 с Python 3.11 создать виртуальное окружение, перенести `backend/`, `requirements.txt` и два исходных CSV в `/opt/healthcore/api/data/`, установить зависимости, скопировать `deploy/server.env.example` в `/opt/healthcore/api/.env`, выполнить `init-db`, два импорта и `train`. Сервисный файл `deploy/healthcore-api.service` запускает Uvicorn от отдельного пользователя `healthcore` только на loopback. Подробные команды для повторного развёртывания находятся в [deploy/README.md](deploy/README.md).

Для Supabase на сервере строку подключения размещают только в `/opt/healthcore/api/.env`, заменяя `DATABASE_URL`; после этого нужна повторная инициализация схемы и импорт в новую БД. Содержимое `.env` нельзя отправлять в Git. Переключение с SQLite на Supabase не переносит данные автоматически. Развёртывание на сервере выполняется только по отдельному запросу владельца.

## Ограничения

Нет февральских фактических значений для итоговой метрики. Нет автоматической очереди/периодического пересчёта, версионируемых миграций, калибровки погодной модели и полного исторического прогона. Графики и экспорт CSV доступны в текущем интерфейсе, но демонстрационный сценарий и точность модели ещё требуют проверки на новых данных.
