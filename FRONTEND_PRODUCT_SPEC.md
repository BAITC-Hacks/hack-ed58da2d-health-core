# Frontend Product Spec: Agentic AI для прогнозирования выработки ВЭС

Дата: 23 сентября 2026 года  
Статус: продуктовый и UX-план вне конкурсного Git-репозитория  
Ответственный: Михаил — product management, UX/UI, Vue 3 frontend, интеграция с API, demo-сценарий

## 1. Продуктовая идея

Сделать интерфейс диспетчера/аналитика ВЭС, который позволяет:

1. выбрать момент выпуска прогноза и горизонт 24 или 48 часов;
2. запустить полный агентный расчет;
3. увидеть почасовой прогноз нормализованной активной мощности;
4. проверить, какие погодные данные и исторический срез использовал агент;
5. проследить этапы агентного цикла и возможные ошибки;
6. последовательно воспроизвести ежедневные выпуски за февраль 2026 года.

Главная продуктовая формулировка:

> Система ежедневно формирует доказуемо честный прогноз выработки ВЭС, используя только ту информацию, которая была доступна на момент выпуска.

## 2. Что интерфейс обязан доказать жюри

Официальные критерии дают по 25 баллов за соответствие задаче, техническую реализацию и воспроизводимость. Поэтому интерфейс должен явно показывать:

- почасовой горизонт ровно 24 или 48 часов;
- момент выпуска прогноза (`issued_at`), отличный от прогнозируемого времени (`valid_at`);
- источник архивного прогноза погоды;
- момент публикации/доступности погодного прогноза;
- исторический cutoff, после которого данные ВЭС не использовались;
- координаты турбины;
- версию модели и идентификатор запуска;
- реальный агентный цикл, а не одну декоративную надпись «AI»;
- повторный расчет после обновления входных данных;
- последовательность ежедневных выпусков за тестовый февраль 2026 года.

Критически важно: фактическая будущая погода не должна отображаться как использованный прогноз. Если архивный прогноз недоступен, интерфейс показывает честную ошибку/предупреждение.

## 3. Целевой пользователь

Основной пользователь MVP — аналитик или диспетчер ВЭС, которому нужно заранее понимать ожидаемый профиль мощности и быстро проверять происхождение прогноза.

Его вопросы:

- сколько энергии/мощности ожидается в каждый следующий час;
- когда ожидаются пики и провалы;
- насколько свежи входные погодные данные;
- завершил ли агент все этапы;
- можно ли доверять временному срезу данных;
- что именно пошло не так, если прогноз не построен.

## 4. Один главный экран

Для хакатона рекомендуется один маршрут `/`, без авторизации и сложной навигации.

### 4.1. Верхняя панель

- название продукта, например `WindSight AI`;
- короткий дескриптор: «Почасовой прогноз выработки ВЭС»;
- состояние API: `Система готова`, `Расчет выполняется`, `API недоступен`;
- время последнего успешного обновления.

### 4.2. Панель запуска прогноза

Поля:

- турбина: в MVP только подтвержденная `Турбина 1`;
- момент выпуска: дата и время, по умолчанию `31.01.2026 00:00`;
- горизонт: сегментированный переключатель `24 часа / 48 часов`;
- кнопка `Запустить агента`;
- вторичная кнопка `Рассчитать февраль`.

Под полями показывать пояснение:

> Агент использует только исторические данные и погодный прогноз, доступные на выбранный момент выпуска.

### 4.3. Карточки результата

После успешного расчета показывать четыре компактных показателя:

- средний прогноз нормализованной мощности;
- максимальный прогноз и время пика;
- минимальный прогноз и время минимума;
- покрытие горизонта: `24/24` или `48/48` часовых точек.

Не подписывать данные как МВт, МВт·ч или кВт·ч, пока backend не передает номинальную мощность и подтвержденную методику пересчета. Базовая единица MVP — `нормализованная активная мощность, 0–1`.

### 4.4. Главный график

График — основной визуальный результат:

- линия/область прогнозируемой нормализованной мощности;
- ось X: локальное время прогнозируемого часа;
- ось Y: диапазон `0–1`;
- tooltip: время, прогноз мощности, скорость ветра, температура;
- вертикальная отметка границы суток;
- при наличии backend-данных — доверительный интервал отдельной полупрозрачной областью;
- под графиком — доступная таблица с теми же значениями.

Нельзя показывать «факт февраля» или метрики ошибки на тестовом периоде без допустимых фактических значений.

### 4.5. Агентный цикл

Показывать вертикальный stepper с реальными статусами backend:

1. `Получение погодного прогноза`;
2. `Проверка временной доступности данных`;
3. `Подготовка признаков`;
4. `Запуск модели`;
5. `Анализ результата`;
6. `Сохранение прогноза`.

Для каждого шага:

- статус `ожидает / выполняется / готово / предупреждение / ошибка`;
- время начала и длительность;
- краткий проверяемый результат;
- сообщение об ошибке без технического мусора и stack trace.

Это не декоративная анимация: состояние должно приходить от backend.

### 4.6. Происхождение данных

Отдельная карточка `Почему этому прогнозу можно доверять`:

- координаты турбины;
- погодный провайдер и ссылка/название набора данных;
- `weather_forecast_issued_at`;
- диапазон `weather_valid_from – weather_valid_to`;
- `historical_cutoff_at`;
- версия модели;
- время расчета;
- предупреждения о пропусках и fallback-логике.

Проверка честности:

- `weather_forecast_issued_at <= issued_at`;
- `historical_cutoff_at <= issued_at`.

Проверку выполняет backend. Frontend отображает результат как `Временная корректность подтверждена` или объясняет нарушение.

### 4.7. Февральский прогон

После запуска batch-задачи показывать:

- общий прогресс, например `9 из 29 выпусков`;
- текущую дату выпуска;
- количество успешных, завершенных с предупреждением и ошибочных выпусков;
- список/таблицу ежедневных запусков;
- действие `Открыть прогноз` для каждой даты;
- возможность повторить только неуспешный выпуск, если backend это разрешает.

Browser не должен сам имитировать последовательность. Он запускает backend-задачу и опрашивает ее статус.

## 5. Состояния интерфейса

Обязательные состояния:

| Состояние | Что видит пользователь |
|---|---|
| Initial | Контролы, объяснение сценария, без выдуманных результатов |
| Loading | Текущий этап агента, прошедшее время, блокировка повторного запуска |
| Success | KPI, график, таблица, этапы, происхождение данных |
| Partial success | Результат есть, но видны конкретные предупреждения |
| Missing weather archive | Архивный прогноз не найден; фактическая погода не подставлена |
| Invalid temporal provenance | Расчет отклонен из-за данных из будущего |
| API/network error | Понятное сообщение и кнопка безопасного повтора |
| Batch running | Прогресс и уже готовые даты доступны без ожидания конца всей задачи |
| Batch partial failure | Успешные даты сохранены, ошибки перечислены отдельно |
| Empty result | Backend завершил задачу без часовых точек; это ошибка, а не успех |

## 7. Предлагаемый API-контракт

Имена маршрутов нужно согласовать с Андреем до реализации frontend.

| Метод | Маршрут | Назначение |
|---|---|---|
| `GET` | `/api/health` | Готовность системы |
| `GET` | `/api/capabilities` | Турбины, допустимые даты, горизонты, часовой пояс |
| `POST` | `/api/forecasts` | Запуск одного выпуска |
| `GET` | `/api/forecasts/{run_id}` | Статус и результат выпуска |
| `POST` | `/api/backtests` | Запуск последовательного февральского прогона |
| `GET` | `/api/backtests/{job_id}` | Прогресс и результаты по датам |

## 8. Визуальное направление

Стиль: технологичный диспетчерский интерфейс, светлый фон, темно-синий текст, бирюзовый основной акцент и желтый цвет предупреждений.

Рекомендуемые токены:

- фон страницы: `#F4F7FB`;
- поверхность: `#FFFFFF`;
- основной текст: `#132238`;
- вторичный текст: `#5F6F82`;
- primary: `#087E8B`;
- success: `#15803D`;
- warning: `#B7791F`;
- danger: `#C2413A`;
- линия графика: `#0E7490`;
- радиус карточек: `12px`;
- расстояния: сетка `4/8/12/16/24/32`.

Не использовать тяжелые фоновые изображения, сложную 3D-анимацию и декоративную карту. Они увеличат риск и не доказывают выполнение кейса.

## 10. Приоритеты MVP

### P0 — обязательно

- один выпуск на 24/48 часов;
- график и таблица почасовых значений;
- реальный статус агентных шагов;
- provenance и временная корректность;
- последовательный февральский batch;
- состояния загрузки и ошибок;
- адаптация под экран ноутбука жюри;
- запуск без личного аккаунта участника.

### P1 — только после рабочего сквозного сценария

- доверительный интервал;
- повтор отдельного ошибочного выпуска;
- экспорт результата в CSV;
- сравнение двух выпусков для одного valid time;
- пояснение ключевых факторов прогноза.

### Не делать в рамках MVP

- авторизацию и роли;
- загрузку произвольных CSV;
- админ-панель;
- поддержку неподтвержденной турбины 2;
- мультиязычность;
- сложную GIS-карту;
- чат с агентом без прямой ценности для сценария;
- декоративные «AI-thinking» сообщения, не связанные с backend.

## 11. План frontend-реализации после появления конкурсного репозитория

1. Согласовать API-контракт и часовой пояс с backend.
2. Создать Vue 3 + Vite каркас непосредственно в выданном репозитории.
3. Реализовать layout и все состояния на одном локальном mock-ответе.
4. Подключить `health`, затем один реальный forecast run.
5. Подключить polling статуса и агентные шаги.
6. Подключить февральский batch.
7. Проверить 24 и 48 точек, границы суток, ошибки и отсутствие погодного архива.
8. Выполнить smoke test по README в чистом окружении.

Каждый содержательный этап — отдельный коммит Михаила и немедленный push в рабочую ветку. Не переносить готовый функциональный frontend из внешней папки.

## 12. Demo-сценарий на 2–3 минуты

1. За 15 секунд сформулировать проблему: выработка ВЭС зависит от погоды, а оператору нужен заранее рассчитанный почасовой профиль.
2. Выбрать выпуск `31 января 2026`, горизонт `48 часов` и нажать `Запустить агента`.
3. Показать, как агент получает архивный прогноз, проверяет временную корректность, готовит признаки и запускает модель.
4. Открыть график и назвать ожидаемый пик/провал.
5. Показать provenance: погодный прогноз был опубликован не позже момента выпуска; история также обрезана по cutoff.
6. Запустить или открыть готовый февральский прогон и показать последовательные ежедневные выпуски.
7. Завершить ценностью: решение превращает модель в воспроизводимый ежедневный процесс принятия решений.

## 13. Frontend Definition of Done

- отображается ровно 24 или 48 последовательных почасовых точек;
- `issued_at` и `valid_at` визуально не смешиваются;
- часовой пояс виден пользователю;
- значения мощности ограничены понятной шкалой 0–1 или явно помечаются как некорректные;
- статусы этапов приходят от backend;
- происхождение погоды и исторический cutoff отображаются;
- отсутствие архивной погоды не маскируется фактической погодой;
- partial failure февральского прогона не уничтожает успешные результаты;
- ошибки понятны без консоли разработчика;
- интерфейс работает на ширине 1280–1440 px и остается пригодным на 768 px;
- основной сценарий повторяется по README без личных аккаунтов;
- frontend не содержит API-ключей и других секретов.

## 14. Вопросы для немедленного согласования с backend

1. Какой часовой пояс считается каноническим для CSV, выпусков и координат ВЭС?
2. Какой именно источник архивных прогнозов погоды используется и какое поле доказывает время публикации?
3. Возвращает ли API промежуточные этапы задачи или только итоговый статус?
4. Batch создает отдельный `run_id` для каждой даты?
5. Как backend сигнализирует о частичном успехе и fallback-данных?
6. Есть ли доверительные интервалы или только point forecast?
7. Подтверждена ли модель только для турбины 1?
8. Есть ли фактические данные февраля, разрешенные для оценки, или метрики показываются только на исторической валидации?
